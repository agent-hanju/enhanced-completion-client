# StreamMerger best effort 성능 비교 (2026-10-17)

실제 제품 구현에서 누적 모델 전체의 후보 복사·재검증·확정·롤백을 제거했다.
목록 검색 사전은 delta 사이에도 유지하며, 새 입력의 일반 값만 복사하고 하위 모델·목록을
직접 병합한다. `result` 조회·오류 보존용 스냅샷은 별도로 복사한다.

## 측정 조건

- Windows 11, Python 3.14.6, 동일 프로세스에서 구현 순서를 교대하여 실행.
- 기존 yield: 복원 기준 `ca14949`의 소스를 별도 모듈로 로딩.
- best effort: 현재 작업 트리의 제품 코드. 임시 실험용 subclass가 아님.
- 입력 생성·모듈 로딩·네트워크 시간은 제외한다.
- 새 병합기 생성 → 입력 전체 apply → 마지막에 결과 한 번 조회한다.
  기존은 build(), 새 구현은 result이다. 결과 model_dump 일치를 먼저 검사한다.
- 일반 입력은 30회씩 7묶음, 블록 증가 입력은 1회씩 7묶음의 회당 중앙값이다.
  짧은 입력의 값은 실행 시점·부하 영향을 받으므로 작은 차이를 일반화하지 않는다.
- timeit 기본 GC 비활성화 조건이며 시간 측정 중 tracemalloc은 비활성화한다.
- 메모리는 별도의 실행에서 최대 추가 할당량을 측정한다. 입력은 미리 만들어 제외한다.
  프로세스 전체 사용량이나 할당 총량은 아니다.
- 후보 원자성 구현 `c841584`은 이번 실행에서 재측정하지 않았다. 원래 측정 JSON과 구현은
  해당 커밋으로 보존되어 있다. 스크립트에서 --skip-atomic을 빼면 함께 측정할 수 있다.

## 해석

블록을 하나씩 추가하는 100·300·1,000델타의 apply 시간은 약 1.64·6.67·20.73 ms다.
목록 검색 사전 재구성으로 생기던 반복 전체 검색을 없앴고, 이 입력에서는 대체로 선형으로
증가한다. 단위 테스트도 1,000델타에서 기존 원소를 매번 다시 검색하지 않는지 확인한다.

동일한 1,000델타 입력의 원자적 전체 복사·검증 버전은 이전 측정에서 약 6.67초였고,
이번 best effort는 마지막 조회 포함 약 34.57 ms다. 서로 다른 실행의 참고 비교이며
정확한 배율 보증으로 해석하지 않는다. 기존 yield보다 모든 입력에서 빠른 것은 아니다.
특히 Pydantic 모델을 직접 보관·변경하는 비용과 공개 API로 스냅샷을 복사하는 비용은 남는다.
1,000델타의 apply만 최대 메모리는 약 0.80 MiB로 기존 0.45 MiB보다 높지만,
마지막 결과 조회 포함 최대값은 약 1.62 MiB로 기존 2.03 MiB보다 낮았다.

모든 입력이 선형이라는 뜻은 아니다. 일반 문자열의 반복 연결과 조립 중인 도구 인수 JSON
파싱은 누적 문자열 길이에 따른 비용이 있다. 매 delta마다 result를 조회하면 전체 스냅샷
비용도 반복된다. RuntimeExecution은 내부에서 매 delta마다 스냅샷을 만들지 않고
active_response 조회 시에만 생성한다. Bridge의 좌표 정렬 비용은 병합기 단독 측정 밖이다.
