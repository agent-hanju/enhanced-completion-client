# StreamMerger 모델 확정 방식 성능 비교 (2026-10-17)

매 delta의 후보 병합·검증 후 모델 참조를 교체하는 구현과 기존 yield 누적기를 비교했다.
기존 구현은 delta별 원자성·검증을 제공하지 않으므로 같은 계약을 충족하는 대안이 아니라
기능 변경 비용을 알아보기 위한 기준이다. 기존 프레임·작업 클래스 구현은 현재 코드와
측정 도구에서 제거했다. 복원 기준은 `ca14949`다.

## 측정 조건

- Windows 11, Python 3.14.6, 같은 프로세스에서 두 구현을 교대 실행.
- 기존: `ca14949`의 merge.py를 별도 모듈로 로딩. 새 구현: 현재 모델 확정 구현.
- 입력 생성, 모듈 로딩, 네트워크는 제외.
- 각 회는 새 병합기 생성 → 입력 전체 apply → 마지막에 결과 한 번 조회.
- 기존 결과 조회는 build(), 새 구현은 result이다.
- 일반 입력은 10회씩 5묶음, 블록 증가 입력은 1회씩 5묶음의 회당 중앙값.
- timeit 기본 GC 비활성화 조건. 시간 측정 중 tracemalloc은 비활성화.
- 입력마다 두 구현의 최종 model_dump가 같은지 먼저 검사.
- 별도 실행에서 tracemalloc 최대 추가 할당량을 측정. 입력 모델은 미리 생성되어 제외되며,
  프로세스 전체 메모리나 할당 총량이 아니다.
- result 조회 시간은 누적 완료 후 별도 측정. 스트림 중 매 delta마다 조회하는 비용은
  전체 시간 표에 포함하지 않는다. 그런 소비자는 조회 복사 비용이 추가된다.
- 변동 가능한 로컬 미세 측정이므로 작은 차이를 일반적인 우열로 해석하지 않는다.

## 해석과 제한

전체 모델 후보를 매 delta마다 복사·검증하는 방식은 짧은 스트림에서도 비용이 늘었다.
서로 다른 블록이 계속 추가되면 누적 크기에 비례하는 작업을 반복해 총 시간이 제곱으로
증가한다. 1,000블록을 한 delta로 받는 경우와 1,000개 delta로 받는 경우의 차이가 크다.
후자는 약 16.5 ms에서 6.67초로 늘어 약 403배 느렸고 처리량은 약 150 delta/s였다.
메모리도 후보·검증용 데이터와 확정 모델을 동시에 보관하므로 증가했다.

따라서 새 계약은 구현·검증했지만, 이 전체 복사·전체 검증 구현을 성능상 적합하다고
판단할 수 없다. 이 결과를 기준으로 변경한 모델 경로만 후보화·검증하는 방법을 검토해야
한다. 원자성을 없애거나 검증을 종료 시점으로 되돌린 결과를 개선으로 취급해서는 안 된다.

이번 비교에서 최종 결과 조회는 한 번이다. 실제 Bridge의 result는 추가로 seq를 정렬하고
index를 부여하므로 그 비용은 병합기 단독 측정에 포함되지 않는다.
