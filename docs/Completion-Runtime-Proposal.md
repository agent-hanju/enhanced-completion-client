# Completion Runtime 설계 제안

작성일: 2026-10-15
상태: 구현 완료. 아래 내용은 초기 설계이며, 확정한 API와 동작은 [Completion-Runtime.md](Completion-Runtime.md)를 따른다.

구현에서 `Run.tasks`는 `HitlTask` 목록을 제공한다. 각 작업이 `draft: HitlDraft`와 실제 실행을 관리하며, 별도 HITL 목록 및 백그라운드 작업 목록은 보관하지 않는다.

## 1. 목적과 실행 책임

`completion_bridge`에 메시지와 도구 정책을 입력받아 모델 호출과 도구 실행을 자동 진행하는 기능을 추가한다. 기존 `Bridge`는 단일 모델 요청과 응답 변환을 계속 담당하고, `CompletionRuntime`이 Bridge를 사용해 반복 실행한다.

호출자가 실행 객체를 먼저 만들거나 등록할 필요는 없다. 런타임이 내부에서 `Run`을 생성하고, 진행 중 모델 응답을 스트림으로 전달하며, 진행 가능한 처리가 끝나면 실행 결과를 제공한다.

사용자 승인이 필요한 호출 또는 실행 결과가 있으면 그 지점이 이번 실행의 한계다. 라이브러리는 해당 정보를 `HitlDraft`에 기록하고 종료한다. 사용자 결정을 기다리는 태스크, 승인 입력 API, 승인 후 같은 실행 객체를 재개하는 API는 제공하지 않는다.

## 2. 호출 형태

다음은 구현된 기본 호출 형태다. 실행기와 정책의 정의 및 자원 정리는 상세 문서를 참고한다.

```python
from completion_bridge import CompletionRuntime

runtime = CompletionRuntime(bridge=bridge)
execution = runtime.run(messages, tools=tools, policy=policy)

async for delta in execution:
    print(delta.text, end="")

result = execution.result
```

스트림을 직접 소비하지 않을 때는 같은 실행을 일괄 소비한다.

```python
result = await runtime.complete(messages, tools=tools, policy=policy)
```

- `messages`는 `HubMessage` 목록이며, 중첩 블록까지 복사해 호출자의 입력과 독립적으로 관리한다.
- `tools`는 모델에 제공할 도구 정의와 실제 실행 기능을 제공한다.
- `policy`는 실행 전 승인 정책과 실행 후 검토 정책을 판정한다.
- 모델 및 생성 설정은 기존 Bridge의 호출 설정을 활용한다.
- 호출마다 독립된 `Run`을 생성한다. 실행 등록소나 ID 기반 조회는 요구하지 않는다.
- 모델 출력은 기존 `HubResponse` 델타 계약을 유지한다. 서로 다른 모델 요청의 델타를 하나의 응답처럼 병합하지 않는다.
- `execution.result`는 정상적인 실행 종료 후 제공하고, `execution.partial`은 진행 중이나 오류·취소 후 확보한 상태를 제공한다.
- `run()`은 실행 객체를 반환하고, 비동기 반복으로 진행 중 모델 출력을 소비한다. 실제 실행 시작 시점은 구현에서 명시한다.
- `complete()`는 같은 실행을 끝까지 소비하고 `Run`을 반환한다. 두 방식 모두 백그라운드 작업 핸들에 접근할 수 있어야 한다.
- `execution.result` 제공은 메인 실행 종료를 뜻한다. 전체 백그라운드 작업 완료와는 구분한다.

## 3. 실행 객체와 결과 `Run`

`run()`은 스트림 소비와 실행 수명 관리를 제공하는 실행 객체를 반환한다. 라이브러리의 `Run`은 실행 입력과 결과, 진행 중인 백그라운드 작업의 핸들을 보관한다. 서버 태스크나 HTTP 연결을 관리하는 `common-hitl-chat`의 `Run`과는 별도 타입이다. 구체적인 필드 이름은 구현 설계에서 확정한다.

| 정보 | 내용 |
|---|---|
| 입력 메시지 | 이번 실행에 전달한 이력의 독립 복사본 |
| 생성 메시지 | 모델 응답과 모델에 전달할 수 있는 도구 결과 |
| 모델 응답 | 요청별 응답과 사용량, 중단·차단 사유 |
| HITL 기록 | 호출별 `HitlDraft` 목록 |
| 상태와 종료 사유 | 최종 답변, 사용자 승인 필요, 제한 도달, 오류, 취소 등의 구분 |
| 부분 결과 | 완료 전에 확보한 모델 응답과 도구 실행 기록 |
| 백그라운드 작업 | 작업별 상태 조회, 결과 대기, 취소에 사용하는 핸들 |

입력 이력과 이번 실행의 생성 메시지는 구분한다. 실행 후 검토가 필요한 원본 결과는 `HitlDraft.execution`에 보존하되, 모델에 제공할 도구 결과 메시지로 추가하지 않는다.

## 4. `HitlDraft` 사용

별도 `ToolExecutionRecord`를 만들지 않고, `common-hitl-chat`의 `HitlDraft`와 필요한 하위 데이터 모델을 같은 이름과 구조로 가져온다. 해당 서버 패키지를 의존성으로 추가하거나 그 클래스를 직접 import하지 않는다.

현재 소스에서 확인한 `HitlDraft` 구조를 유지한다.

| 필드 | 역할 |
|---|---|
| `call` | `ToolCall`: 원본 호출 ID, 도구 이름, 인자, 블록 순서 |
| `created_at` | 기록 생성 시각 |
| `approval`, `review` | `HitlDecision`: 실행 전·후 판정 |
| `execution` | `Execution`: 실제 실행 결과와 실행 시각 |
| `error` | 호출 처리 오류 |
| `background` | 백그라운드 실행 구분 |
| `edited_arguments`, `edited_result` | 외부에서 편집한 인자·결과를 표현하는 기존 필드 |
| `approval_reason`, `review_reason` | 승인·검토 관련 사유 |

`ToolCall`, `HitlDecision`, `Execution`, `ToolPolicy` 등 필요한 데이터 타입도 함께 구성한다. 서버 전용 `UserId` 같은 참조 타입은 기존 값 형식과 검증 규칙을 확인해 서버 패키지 없이 표현한다. 저장 모델, 프로필, FastMCP 실행기는 가져오지 않는다.

편집 필드와 판정 출처를 유지하는 것은 데이터 구조를 유지하기 위한 것이며, 라이브러리가 사용자 승인이나 편집 적용 기능을 제공한다는 뜻은 아니다.

## 5. 자동 실행과 종료

1. 입력을 복사해 내부 `Run`을 생성한다.
2. Bridge 스트림을 소비하며 델타를 호출자에게 전달하고 요청별 응답을 보관한다.
3. 완료한 모델 응답을 생성 메시지에 추가한다.
4. 도구 호출이 없으면 최종 답변으로 종료한다.
5. 도구 호출별 `HitlDraft`를 만들고 실행 전 정책을 판정한다.
6. 허용한 호출을 실행하고 실행 후 정책을 판정한다.
7. 모델에 제공할 수 있는 결과를 생성 메시지에 추가한다.
8. 사용자 승인이 필요하면 종료하고, 일반 호출의 결과 또는 백그라운드 호출의 접수 결과가 준비됐으면 후속 모델 호출을 진행한다.

| 단계와 판정 | 처리 |
|---|---|
| 실행 전 `ALLOW` | 도구 실행 |
| 실행 전 `ASK` | 실행하지 않고 판정을 기록한 뒤 사용자 승인 필요로 종료 |
| 실행 전 `DENY` | 실행하지 않고 거절 결과를 기록하고 모델용 결과 생성 |
| 실행 후 `ALLOW` | 실행 결과를 후속 모델 요청에 사용 |
| 실행 후 `ASK` | 실제 결과를 기록하되 모델에는 제공하지 않고 사용자 승인 필요로 종료 |
| 실행 후 `DENY` | 실제 결과를 기록하고 원본 대신 거절 결과를 모델에 제공 |

실행 후 거절은 이미 발생한 외부 효과를 취소하지 않는다. 사용자 승인 필요는 정상적인 종료 사유이며, 라이브러리 내부의 결정 대기 상태가 아니다. 승인되지 않은 호출에 임의의 완료 결과를 만들어 후속 모델 요청을 진행하지 않는다.

여러 호출 중 일부가 `ASK`일 때 다른 호출을 어디까지 진행할지는 구현 전에 확정한다. 이미 실행한 결과와 아직 실행하지 않은 호출을 구분해 반환하고, 필요한 도구 결과가 준비되지 않은 상태에서는 다음 모델 요청을 시작하지 않는다.

## 6. 소비 애플리케이션과의 관계

이번 작업에서는 `common-hitl-chat`을 수정하거나 기존 실행 기능을 대체하지 않는다. 해당 프로젝트의 구현은 재사용할 동작과 데이터 구조를 확인하는 참고 소스다.

나중에 연동한다면 라이브러리의 실행 결과를 서버의 `Run`에 반영할 수 있도록 한다. 서버의 `RunRegistry`는 실행 보관, 서버 태스크 수명, 이벤트 구독과 조회를 계속 담당할 수 있다. 라이브러리에서 서버 `Run`이나 `RunRegistry`를 생성하거나 직접 갱신하지 않는다.

입력 이력 조회, 영속 저장, 사용자 인증, 사람의 승인 처리, HTTP/SSE 변환은 소비 애플리케이션이 담당한다. 라이브러리 자체는 DB나 웹 서버를 요구하지 않는다. 주입된 정책 판정기와 도구 실행기가 외부 저장소를 사용하는 것은 별개다. 필수 의존성은 기존 `httpx`, `pydantic`을 유지하는 방향으로 구성한다.

## 7. 추가 실행 동작의 설계 사항

기존 채팅 구현 전체를 대체하는 것이 이번 목표는 아니다. 다음 기능은 기존 제안의 검토 대상으로 유지하되, 자동 실행과 승인 필요 시 종료 계약에 맞는 구체적인 동작을 정한 뒤 구현 범위를 확정한다.

- 에이전트: 독립 입력으로 같은 반복 실행을 사용하고 부모·자식 결과를 구분한다. 자식에서 사용자 승인이 필요하면 부모 결과에서도 그 기록을 확인할 수 있어야 한다.
- 백그라운드 작업: 실행을 시작하고 접수 결과를 모델에 제공할 수 있다. 메인 실행 종료 후에도 진행 중인 태스크의 핸들을 `Run`에서 제공한다. 호출자는 상태 조회, 결과 대기, 취소와 최종 자원 정리를 담당한다. 작업 내부에서 사용자 승인이 필요하면 해당 작업도 `HitlDraft`를 남기고 종료한다.
- 백그라운드 작업은 생성한 프로세스와 이벤트 루프에서 계속 실행된다. Bridge와 도구 연결은 해당 작업이 끝날 때까지 유지해야 한다. 실행 기록은 저장할 수 있지만 실행 중 태스크 자체를 다른 프로세스로 이전하지는 않는다.
- 메인 종료 이후의 백그라운드 결과를 메인 모델에 자동으로 다시 전달하지 않는다. 결과 전달 방식과 이후 처리는 별도 계약으로 명시한다.
- 도구 결과의 답변 대체: 후속 모델 요청 없이 최종 결과로 사용할 조건을 정한다.
- 호출 수 제한: 상한과 초과 호출 처리, 최종 모델 호출 여부를 명시한다.
- 전체 실행 기록과 모델용 결과: `Execution` 원본과 실제 모델에 전달할 내용을 구분한다.

## 8. 오류·취소와 스트림 수명

예상된 도구 실패와 정책 거절은 `HitlDraft` 및 모델용 결과에 기록한다. 모델 통신 실패나 실행을 계속할 수 없는 예외는 부분 상태를 보존하고 호출자에게 전파한다. `complete()`의 예외에서 부분 실행 결과에 접근할 구체적인 방법은 구현 전에 확정한다.

스트림 조기 종료와 취소 시 모델 연결을 정리하고, 이미 발생한 도구의 외부 효과를 취소된 것으로 표현하지 않는다. 정상적인 메인 실행 종료 시에는 반환 결과의 핸들로 백그라운드 작업을 관리한다. 스트림 조기 종료·오류·취소 시 작업을 함께 취소할지와 부분 결과의 핸들로 관리를 인계할지는 구현 전에 명시한다. 참조 없이 남는 태스크가 없도록 한다.

## 9. 예상 구현 규모

| 구성 | 공개 메서드 수 | 비공개 메서드 수 | 책임 |
|---|---:|---:|---|
| `CompletionRuntime` | 2 | 0~2 | `run()`과 `complete()` 진입점 |
| `RuntimeExecution` | 3~4 | 3~5 | 반복 실행, 델타 전달, 결과·부분 결과 제공, 자원 정리 |
| `Run` | 0~1 | 0~1 | 독립 실행의 입력·결과와 백그라운드 작업 핸들 보관 |
| 백그라운드 작업 핸들 | 2~3 | 0~2 | 상태·결과 접근, 완료 대기와 취소 |
| `HitlDraft`, `ToolCall`, `Execution` | 각각 0 | 각각 0~1 | 기존 데이터 구조 유지와 필요한 검증 |
| `HitlDecision` 및 정책 값 타입 | 각각 0~1 | 각각 0~1 | 단계별 판정 데이터 |
| 도구 실행기 Protocol | 1~2 | 0 | 도구 정의와 실제 실행 계약 |
| 정책 판정기 Protocol | 2 | 0 | 실행 전·후 정책 판정 계약 |

별도 실행 등록소, 사용자 승인 관리자, `ToolExecutionRecord`는 추가하지 않는다. 메서드는 100줄 이내를 예상하며 길이만을 이유로 기계적으로 분할하지 않는다. 특수 알고리즘이나 자료구조는 현재 예상하지 않는다. 백그라운드 작업 핸들은 위 표에 포함한다. 에이전트의 상세 구성은 동작 확정 후 추가 산정한다.

## 10. 검증 기준

1. 입력과 중첩 블록을 변경하지 않고 내부 실행 객체를 생성한다.
2. 도구 없는 요청의 델타와 최종 실행 결과를 제공한다.
3. 자동 허용된 호출을 실행하고 결과를 사용해 후속 모델 요청을 수행한다.
4. 실행 전 `ASK`에서는 도구 실행과 후속 모델 요청 없이 기록을 반환한다.
5. 실행 후 `ASK`에서는 실제 결과를 보존하고 모델에는 제공하지 않은 채 반환한다.
6. 정책 거절과 도구 실패를 기록 및 모델용 결과에 일관되게 반영한다.
7. 여러 모델 요청의 델타를 전달하면서 요청별 응답을 독립적으로 보존한다.
8. 일괄 실행과 스트림 실행의 최종 결과가 일치한다.
9. 오류·취소·스트림 조기 종료에서 부분 결과와 자원 정리 계약을 지킨다.
10. DB·웹 서버·실행 등록 없이 동작하고 기존 Bridge의 공개 계약과 테스트를 유지한다.
11. 메인 실행 종료 후 백그라운드 작업의 상태 조회·결과 대기·취소를 할 수 있다.
12. 백그라운드 작업의 승인 필요 종료와 오류를 기록하고, 최종 정리 후 남은 태스크가 없다.

구현 전에 여러 도구 호출의 처리 순서, 스트림의 요청 구분 방법, 예외의 부분 결과 접근, 추가 실행 기능의 범위를 확정하고 위 클래스·메서드 규모를 검토한다.


## 11. 확정한 실행 계약

- 첫 비동기 소비 시 시작하며 입력과 도구 정의는 `run()`에서 복사한다.
- `Run.tasks`의 `HitlTask`가 기록과 대기·취소를 제공한다. `Run.aclose()`는 자식 작업까지 정리한다.
- 응답의 모든 호출을 먼저 기록하고 순서대로 실행한다. `ASK` 이후 호출은 미실행 상태로 반환한다.
- 요청 구분은 `execution.request_index`, 요청별 결과는 `Run.responses`로 제공한다.
- 예외는 부분 결과를 제공하는 `RuntimeErrorWithPartial`, 취소는 `RuntimeCancelled`를 사용한다.
- 조기 종료·오류·취소 시 백그라운드 작업도 취소·회수하며 정상 종료 후에는 호출자가 관리한다.
- `max_tool_calls` 기본값은 32이며 제한 도달 후 추가 모델 호출은 하지 않는다.
- 검토를 통과한 `ToolOutput.final=True` 결과는 후속 모델 요청 없이 답변을 대체한다.
- `AgentToolExecutor`가 독립 자식 실행을 제공하며 승인 필요 상태와 원본 기록을 부모에서 확인할 수 있다.

현재 검증은 모의 HTTP를 사용하는 실제 Bridge 통합 테스트 및 오프라인 회귀 테스트다.
외부 모델·MCP 서비스에 대한 라이브 실행은 포함하지 않는다.
