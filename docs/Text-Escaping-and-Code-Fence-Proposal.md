# 제안: 기본 text path 치환과 코드 펜스의 transition 억제

상태: 기능 제안. 현재 제공되는 API가 아니며 구현·릴리스 일정도 가정하지 않는다.
작성일: 2026-10-21
요청 소비 프로젝트: common-hitl-chat

## 필요한 사용 사례

common-hitl-chat은 native API가 제공하지 않는 인용 구조를 응답의 text stream에서 추출한다.
애플리케이션 소유 vocabulary가 `<CIT id="문서 ID" origin="문서 제공자">답변</CIT>`를
`CiteBlock(text, id, origin)`으로 변환하고, 이전 답변을 재전송할 때 같은 태그로 직렬화한다.
태그와 속성의 의미, 문서 연결, 저장·표시는 소비 애플리케이션의 책임이다.

모델은 같은 문자열을 XML 예제, 로그, JSON 문자열, 코드 작성 요청에 대한 응답으로도 출력할 수 있다.
현재 태그 파서는 코드 펜스 여부를 판단하지 않으므로 이런 출력도 등록된 transition으로 해석한다.
사용자 입력·검색 결과·도구 결과의 리터럴 태그가 다음 모델 요청에 재사용되는 경우도 있다.

일부 로컬 모델 실험에서는 비인용 태그를 escape하도록 시스템 프롬프트에 명시해도 코드·XML 형식
요청에서 실제 태그를 출력했다. 이는 코드 작성 형식에 관한 학습 경향이 출력에 강하게 작용할 수
있다는 문제 사례이며, 코드 펜스 토큰이 시스템 메시지보다 높은 우선순위를 갖는다는 측정 결과는 아니다.
text 내부 구조를 해석하는 라이브러리는 시스템 프롬프트만으로 리터럴 표기를 통제할 수 있다고
가정하지 않는 편이 좋다.

## 책임과 도입 조건

| 담당 | 책임 |
| --- | --- |
| 소비 애플리케이션 | Bridge 초기화 시 문자열 쌍과 적용 옵션 명시, 그 계약에 맞는 출력 가이드 작성 |
| Bridge | 요청 직렬화 시 치환, 응답 파싱 후 복원, 스트리밍 상태·flush·부분 결과의 일관성 |
| Vocabulary | 사용자 정의 블록의 태그 문법과 블록 변환 |
| TagParser | 등록된 transition 판정과 선택적인 코드 펜스 인식 |

소비 서버는 기존 도메인 데이터를 그대로 Bridge에 전달하고 반환된 HubResponse를 저장한다.
ChatService에 별도 치환기, 응답 후처리기 또는 자체 스트림 버퍼를 추가하지 않는다.
등록한 인식 문자열은 저장과 애플리케이션 처리의 기준이며 대체 문자열은 LLM 통신 표기다.
이 기능은 태그의 리터럴 표기를 구별하는 계약이며 모델의 일반적인 지시 준수를 보장하지 않는다.

common-hitl-chat의 도입과 시스템 프롬프트 변경은 라이브러리 기능이 제공된 후 별도로 검토한다.
이 제안 작성만으로 소비 서버의 동작이나 의존 버전을 변경하지 않는다.

## 외부 설정 API 제안

아래는 희망하는 사용 형태를 설명하는 의사 코드다. 현재 생성자가 받는 인자가 아니다.

```python
bridge = Bridge(
    # 기존 vendor, base_url, model, vocabularies 등
    text_path_replacements=(("<CIT", "&lt;CIT"),),
    text_path_input_roles=("user", "assistant", "tool"),
    code_fences_literal=True,
)

# 기존 HubMessage를 전달한다. 호출부에서 replace()를 수행하지 않는다.
stream = bridge.stream(messages)
```

- 문자열 쌍은 `(인식 문자열, 대체 문자열)` 순서이며 추가 등록할 수 있다.
- 기본값은 빈 문자열 쌍 목록과 `code_fences_literal=False`로 기존 동작을 유지한다.
- SyncBridge에도 같은 설정을 제공한다.
- `text_path_input_roles`는 호출자가 지정하는 입력 적용 정책이다. 위 예에서는 출력 규칙을 설명하는
  system 메시지를 그대로 전송한다. role이 데이터의 신뢰성을 보장한다는 뜻은 아니다.
  system 템플릿에 외부 데이터를 삽입하는 호출자는 그 데이터의 처리 정책도 명시해야 한다.
- 비스트리밍 완료, 스트리밍, 요청 미리보기, 토큰 수 계산이 같은 요청 직렬화를 사용한다.
- Bridge 인스턴스에 보관하는 설정은 변경 불가능한 사본으로 관리하고 스트림 상태는 요청별로 생성한다.

## 기본 text path에 한정한 치환

이 제안에서 기본 text path는 등록된 사용자 정의 transition으로 진입하지 않은 루트 경로 `/`다.
단순히 모든 블록에서 이름이 `text`인 필드를 찾는 동작을 뜻하지 않는다.

### 입력

1. 적용 대상 role의 일반 TextBlock을 기본 text path의 데이터로 취급한다.
2. 인식 문자열을 대체 문자열로 한 번 치환한다. 원본 HubMessage는 수정하지 않는다.
3. 그 후 vocabulary가 구조화 블록을 실제 transition 태그로 직렬화한다.
4. 최종 요청 본문 전체에 일괄 치환을 수행하지 않는다.

| 도메인 입력 | LLM에 제공할 값 |
| --- | --- |
| `TextBlock(text='<CIT id="d">예시</CIT>')` | `&lt;CIT id="d">예시</CIT>` |
| `CiteBlock(id='d', origin='rag', text='근거')` | `<CIT id="d" origin="rag">근거</CIT>` |
| 적용 대상에서 제외한 system의 `<CIT ...>` 출력 지침 | 원래 지침 그대로 |

custom path의 본문·속성, tool arguments, native payload, 서명·암호화 추론, URL, 바이너리 데이터는
이 기본 text path 기능으로 일괄 변환하지 않는다. 예를 들어 `CiteBlock.text` 내부의 리터럴 문법은
해당 vocabulary의 직렬화 계약에서 결정하며 이 제안의 자동 치환 범위에 포함하지 않는다.
검색·도구 블록을 vocabulary가 일반 텍스트로 만든다는 이유만으로 전체 결과를 자동 치환해서도 안 된다.
그 결과에는 vocabulary가 생성한 문법과 데이터가 함께 있을 수 있기 때문이다.
그런 데이터까지 지원하려면 vocabulary가 기본 text path의 데이터 조각을 구별하여 Bridge의
공통 직렬화 처리를 사용하도록 확장해야 한다. 소비 서버의 자체 replace()로 보완하지 않는다.

### 출력

1. 모델이 출력한 실제 transition 문법을 먼저 파싱한다.
2. 모든 활성 transition 판정이 완료된 기본 text path의 문자열에서 대체 문자열을 복원한다.
3. 복원된 문자열을 다시 transition 파서에 전달하지 않는다.
4. 호출자가 받는 delta, 최종 result, 취소·실패 시 partial에는 같은 복원 규칙을 적용한다.

| 모델 출력 | 소비자가 받는 결과 |
| --- | --- |
| `&lt;CIT id="d">예시</CIT>` | 원래 `<CIT ...>` 표기가 있는 일반 TextBlock |
| `<CIT id="d" origin="rag">근거</CIT>` | vocabulary가 만든 CiteBlock |
| custom path 내부의 `&lt;CIT` | 기본 경로 치환으로는 복원하지 않음 |
| 기본 경로의 `&amp;` 등 미등록 문자열 | 원문 유지 |

각 delta에서 단순 replace()를 호출해서는 `&lt;CI`와 `T`로 분할된 입력을 처리할 수 없다.
블록·seq·경로별로 미확정 접미사만 보관한다. 서로 다른 경로 또는 블록의 문자를 합쳐 매칭하지 않는다.
정상 종료와 취소·실패 시 남은 미완성 대체 문자열은 받은 내용 그대로 보존한다.
복원이 문자열 길이를 바꾸므로 벤더 인용·annotation의 문자 좌표가 함께 제공되는 경우에는 위치 변환
계약도 정의해야 한다. 수정 전 좌표를 수정 후 텍스트의 좌표처럼 제공해서는 안 된다.

### 문자열 쌍의 의미와 검증

- 비어 있는 문자열, 같은 인식 문자열의 중복, 같은 대체 문자열의 중복, 양쪽이 동일한 쌍을 거부한다.
- 여러 쌍을 한 번의 왼쪽부터 처리하는 방식으로 적용하며 동일 위치에서는 긴 매치를 우선한다.
  치환으로 새로 생성된 문자열은 같은 호출에서 다시 치환하지 않는다.
- `<CIT` → `&lt;CIT`만 등록하는 구성은 예약 표기 규약이다. 원래 `&lt;CIT`였던 입력도 모델이
  같은 표기로 출력하면 `<CIT`로 복원되므로 임의 문자열에 대한 무손실 왕복이라고 설명하지 않는다.
- 두 표기를 모두 문자 그대로 보존해야 한다면 예를 들어 `&` → `&amp;`를 추가한 단일 패스 구성을
  검토할 수 있다. 이때 원래 `&lt;CIT`는 `&amp;lt;CIT`로 전송하고 한 번 복원하여 `&lt;CIT`로 남긴다.
  교차하는 임의 쌍 전체의 가역성을 보장한다고 가정하지 말고 지원하는 쌍의 제약과 검증을 확정해야 한다.

## 코드 펜스 안에서 transition 억제

`code_fences_literal=True`일 때 파서는 코드 펜스 안의 태그를 일반 텍스트로 취급한다.
코드 펜스 자체를 제거하거나 새로운 CodeBlock으로 변환할 필요는 없다.

- 바깥에서 펜스를 시작하면 펜스가 끝날 때까지 사용자 정의 transition을 수행하지 않는다.
- 이미 custom path인 상태에서 펜스를 시작하면 그 path를 유지한다. 펜스 안의 종료 태그 때문에
  custom path를 종료하지 않는다. 펜스가 끝나면 기존 path의 transition 판단을 재개한다.
- 기본 경로에서 펜스를 시작했다면 그 텍스트도 기본 경로이므로 등록한 대체 문자열 복원을 적용한다.
- 실제 `<CIT ...>`를 코드 펜스에 출력해도 인용 블록이 생기지 않는다. 펜스 밖에서는 기존대로 해석한다.
- 인라인 백틱, 들여쓰기 코드 블록, native API tool/citation/thinking 이벤트의 해석은 변경하지 않는다.

일반 fenced code 표기를 기준으로 백틱·틸드 3개 이상, 같은 문자로 된 충분한 길이의 종료 펜스,
최대 3칸의 선행 공백, info string, CRLF를 처리한다. EOF까지 종료하지 않은 펜스의 내용도
리터럴 텍스트로 유지한다. 기준 문법은 [CommonMark fenced code blocks](https://spec.commonmark.org/0.31.2/#fenced-code-blocks)를
참고하되 blockquote·list 내부 접두사까지 인식할지는 upstream 설계에서 명시해야 한다.
초기 지원을 최상위 펜스로 제한한다면 그 제한과 중첩 컨테이너의 미지원 사례를 문서와 테스트에 표시한다.
시작·종료 펜스와 태그가 어떤 스트림 조각으로 분할되어도 결과가 같아야 한다.

모델 출력 예시:

````text
태그 예시는 다음과 같습니다.
```xml
<CIT id="sample" origin="rag">이것은 예시입니다.</CIT>
```
<CIT id="real" origin="rag">이 문장은 실제 인용입니다.</CIT>
````

희망 결과는 코드 예제를 보존한 TextBlock과 마지막 문장의 CiteBlock이다.
기능을 비활성화하면 코드 예제의 태그도 현재의 transition 규칙에 따라 해석한다.

## 구현 검토 위치와 규모

현재 소스 기준으로 `bridge.py`의 `_Lowerer`는 vocabulary를 순서대로 적용하고, `_Pipeline`도
등록된 lift mapper를 순서대로 실행한다. `streaming/content.py`의 TagParser는 경로를 관리한다.
이 세 부분과 vocabulary 생성 계약에 설정을 전달하는 방법을 우선 검토한다.

외부 vocabulary는 현재 `lift_mapper()` 내부에서 `TagParser(schema)`를 직접 생성할 수 있다.
따라서 Bridge 생성자에 인자만 추가해도 기존 파서가 그 설정을 알게 된다고 가정할 수 없다.
명시적인 파서 설정 전달 계약과 기본 경로 출력의 식별 방법이 필요하다. 첫 vocabulary에서 복원한
문자열을 다음 vocabulary가 다시 태그로 해석하는 구현은 허용하지 않는다.

예상 책임 단위는 다음과 같다. 실제 클래스명과 API는 구현 시 upstream에서 확정한다.

| 구성 | 책임 | 추가 공개 메서드 예상 | 추가 비공개 메서드 예상 |
| --- | --- | --- | --- |
| 불변 설정 모델 | 쌍·적용 role·펜스 옵션 검증 | 0~1 | 0~1 |
| 기본 경로 text codec | 단일 패스 치환과 점진적 복원 | 2~3 | 1~2 |
| TagParser 확장 | 펜스 상태와 기존 path 유지 | 0 | 1~2 |
| Bridge 설정 전달 | 요청·응답의 동일 옵션 적용 | 0~1 | 1~2 |

100줄을 초과하는 새 메서드는 목표로 하지 않는다. 점진적 문자열 인식은 분할 입력에 대한 알고리즘
검증이 필요하지만 전문 자료구조를 도입할 필요는 예상하지 않는다. 여러 외부 vocabulary의 설정 전달이
기존 계약을 바꿀 수 있으므로 특정 클래스 하나만 바꾸면 충분하다고 약속하지 않는다.

## 수용 테스트

1. 리터럴 `<CIT` 입력, 진짜 CiteBlock, system 출력 지침을 같은 요청에서 구분한다.
2. 기본 경로와 custom path에서 같은 대체 문자열이 다른 처리 범위를 갖는지 확인한다.
3. 문자열·펜스·태그의 모든 분할 위치에서 비분할 입력과 같은 결과를 얻는다.
4. 짧거나 다른 문자로 된 종료 후보, CRLF, info string, EOF 미종료를 확인한다.
5. custom path 내부 펜스와 기본 경로 펜스, 기능 on/off를 각각 확인한다.
6. 원본 메시지 불변, 스트림 간 상태 격리, delta 병합과 result·partial의 일치를 확인한다.
7. 복원 문자열이 후속 vocabulary에서 다시 파싱되지 않는지 확인한다.
8. 미등록 엔티티·native payload·서명·tool arguments·custom attrs의 원문 보존을 확인한다.
9. 문자 좌표가 있는 벤더 인용과 치환이 함께 있을 때 수정된 텍스트의 위치 계약을 검증한다.
10. 소비 애플리케이션에 치환 코드 없이 Bridge 초기화 옵션만으로 사용하는 통합 예제를 제공한다.
